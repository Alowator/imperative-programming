# lectureX16

============== Динамическое выделение памяти ===============

malloc/free — функции выделения/освобождения блоков памяти в куче

Почему может быть нужно реализовывать своё выделение памяти:
1) Нет кучи вообще.
Такое бывает в программировании для встроенных систем (embedded programming).
Хотя в этой области предпочитают обходиться без кучи вообще.
2) Куча есть, но работает недостаточно быстро/хорошо.

В этой лекции будем предполагать второй вариант.
В таком случае куча уже есть, но хочется уменьшить количество malloc/free для улучшения эффективности.

Обычно писать собственное выделение памяти имеет смысл только в том случае,
если нам известно что-то о характере запросов, что неизвестно реализации malloc/free из CRT.
Мы будем далее предполагать, что все выделяемые блоки памяти имеют одинаковый размер.
(хотя многие рассматриваемые приёмы работают и для блоков разного размера)

============== Объекты фиксированного размера ==============

Бывает такое, что нужно выделять память под много объектов одного типа.
При этом размеры всех блоков памяти одинаковы, что позволяет выделять память быстрее.

Пусть размер объекта S байт.
Выделим сразу буфер памяти под B блоков — размера B*S байт:

```
  +---+---+---+---+---+---+---+---+---+---+---+---+
```

ptr–>| A | B | C | D | E | F | G | | | | | |
+—+—+—+—+—+—+—+—+—+—+—+—+
^ (занятые ячейки) ^ (свободные места)
| |
k — кол-во занятых >>>

Будем на выделения памяти возвращать последовательно ячейки массива.
Тогда выделение памяти становится почти бесплатным:
MyObj *allocMyObj() {
return ptr[k++];
}

Конечно, подобный способ выдачи памяти подряд из заранее выделенного куска работает и для объектов разного размера.
Этот способ иногда называют “linear allocator”, т.к. он линейно идёт по памяти и выдаёт её страждущим.

> Что делать, когда свободные места в буфере закончатся?
> 

realloc этого буфера нельзя делать, т.к. адреса выделенных блоков должны сохраняться.

Можно выделить в куче новый буфер, и продолжать работать с ним.
Через какое-то время получится цепочка буферов (chunk’ов): >>>
|
/-+—+—+—+—+—+—+-  /-+—+—+—+—+—+—+-  /-+—+—+—+—+—+—+-

chunks<–>#| A | B | C | D | E | F |#<–>#| G | H | I | J | K | L |#<–>#| M | N | O | | | |#<—–>chunks
-+—+—+—+—+—+—+-/ -+—+—+—+—+—+—+-/ -+—+—+—+—+—+—+-/
(полный буфер) (полный буфер) занято ^ свободно
(текущий буфер)
Хранение цепочки в связном списке любого вида (лучше конечно двусвязный кольцевой с sentinel).
В последнем буфере храним количество занятых мест (оно постепенно растёт).

> Что делать с удалением/освобождением объектов?
> 
1. Ничего!
Можно удалить все объекты разом в конце работы: назовём эту операцию freeAll.
Плюс: это работает очень быстро (кстати, free обычно работает медленнее malloc).
Минус: в условии постоянного создания и удаления объектов может быть больший перерасход памяти, т.к. такой аллокатор пустые места не переиспользует.
Требуется памяти на C объектов, где С — общее количество создаваемых объектов.

Очень удобно для временной памяти, для которой точно известно, когда она станет не нужна, и что её мало.
(кстати, в принципе работает и для блоков разного размера)

1. Можно разрешить “откатывать назад” состояние.
Это работает примерно так:
mark = save(); //сохраняем в mark состояние: указатель на текущий буфер и количество занятых мест в нём
… (выделяем временные объекты)
rollback(mark); //возвращаем обратно сохранённое состояние
По сути, после отката к какому-то моменту времени все объекты, созданные после него, удаляются автоматически.
Иными словами, разрешено удалять только последний живой объект — ограничение на порядок удалений.
Сохраняемое сосотяние — это всего лишь указатель на последний буфер и количество выделенных объектов в нём.

По этому же принципу работает выделение памяти на стеке (для локальных переменных).
Поэтому такой принцип называется “stack allocator”.
Хорошо сочетается с рекурсией. Работает для аллокации блоков разного размера.

1. Можно отмечать положения удаляемых объектов и переиспользовать их в будущем.
Классический способ реализации называется “free list”.
Идея такая: будем хранить связный список всех доступных для переиспользования ячеек.
Для экономии памяти, будем хранить каждый узел списка прямо в соответствующей ячейке (ведь они в этот момент не заняты).
/——–<——-
/
/— /-+- 
/ / | 
/-+—+-^-+—+-v-+—+—+- /-+—+-v-+-v-+-^-+—+—+- /-+-^-+—+—+—+—+—+-
chunks<–>#| A |%%%| C |%%%| T | F |#<–>#| W |%%%|%%%|%%%| K | S |#<–>#|%%%| N | Q | | | |#<—–>chunks
-+—+-^-+—+-v-+—+—+-/ -+—+-v-+-v-+-^-+—+—+-/ -+-^-+—+—+—+—+—+-/
| / / / | ^ свободно
NULL <——-+—–/ / / | / |
-———–<———–/ freeList

void alloc() {
if (!freelist)
allocateNewChunk(); //все ячейки нового буфера добавляются в freelist
assert(freelist);
void *res = freelist;
freelist = freelist->next;
return res;
}
void free(void* ptr) {
((FreeNode*)ptr)->next = freelist;
freelist = (FreeNode*)ptr;
}

Операции по-прежнему работают за O(1), а памяти нужно на (L + B) объектов,
где L — максимальное количество живых объектов на какой-либо момент, а B — размер блока.

Заметим, что ячейки в freeList могут попадать в любом порядке.

> Необычное: система слотов.
Имея указатель на потенциальной удалённый объект, можно ли определить, жив он или нет?
> 

В случае malloc/free ответ — нельзя.
Потому что если объект удалён, на его месте могут быть любые данные, а т.ч. даже новый объект этого же типа (подозрительной похожий на старый).
Глядя на записанные данные нельзя никак определить подобную ситуаций.
Проблему можно решить, если в ссылках на объект хранить не только адрес/указатель, но ещё дополнительную информацию.

Пример: создание/удаление игровых объектов в Doom 3.
Все они хранятся в одном глобальном массиве entities размером 4096 ячеек.
(никакой цепочки блоков нет: если все ячейки заняты, новые игровые объекты просто перестают создаваться — нормальная практика в мире gamedev)

Для каждого объекта будем поддерживать два числа:
int pos; //номер ячейки массива entities, где лежит объект
int spawnIdx; //номер операции создания объекта, которая породила этот объект
То есть мы будем нумеровать все операции создания игровых объектов по очереди.
Первый созданный объект получает spawnIdx = 0, второй spawnIdx = 1, третий spawnIdx = 2, и так далее.
spawnIdx показывает момент времени, когда объект был создан (по аналогии с тем, как работает “время выхода” в обходе графа в глубину)

Будем хранить spawnIdx и в самом объекте, и в каждой ссылке на него.
В каждой ссылке на игровой объект будем хранить и номер ячейки, и его spawnIdx:
struct EntityPtr { //ссылка на игровой объект
uint16_t pos; //номер ячейки в массиве entities, в котором лежал объект (в момент создания ссылки)
uint16_t spawnIdx; //spawnIdx для того объекта, на который указывает эта ссылка
};

Тогда если объект был удалён и его место переиспользовано, то в entities[ptr.pos] будет записан другой spawnIdx.

```
Entity entities[4096];
Entity *Get(EntityPtr ptr) {      //"разыменование" нашей ссылки
    return &entities[ptr.pos];
}
int IsPtrDead(EntityPtr ptr) {    //верно ли, что объект по ссылке умер?
    return Get(ptr)->spawnIdx != ptr.spawnIdx;
}
EntityPtr CreateEntity() {
    EntityPtr ptr;
    ptr.pos = freeList.pop();     //свободные ячейки массива хранятся в списке
    Get(ptr)->spawnIdx = ptr.spawnIdx = spawnCount++;
    return ptr;
}
void DeleteEntity(EntityPtr ptr) {
    Get(ptr)->spawnIdx = -1;      //при удалении очищаем spawnIdx
    freeList.push(ptr.pos);
}
```

================ Аллокатор общего назначения ===================

Если есть кусок памяти, и в нём нужно выделять блоки памяти разного размера, то в общем случае ситуация выглядит так:

+—————–+—+–+—–+-+———+-+-+-+–+——–+—+–+——+-+
| |###|##| |#|#########|#|#| |##| |###|##| |#|
+—————–+—+–+—–+-+———+-+-+-+–+——–+—+–+——+-+

Весь управляемый отрезок памяти = последовательность свободных и занятых блоков.
Обычно свободные блоки разделены занятыми — при освобождении памяти соседние свободные блоки нужно склеивать (coalescing).
Нужно немало дополнительных данных, чтобы работать с этой структурой:
размеры блоков / связный список всех блоков
связный список свободных блоков

Главная проблема возникает при выделении: нужно найти свободный блок подходящего размера.
Проход по связным спискам может работать за O(F) времени в худшем случае, где F — количество свободных блоков.
Есть разные стратегии для сокращения этого времени в среднем на практике.

> Что добавляет многопоточность?
Системная куча обычно одна на всю программу, а значит все потоки должны работать с ней одновременно.
При каждом выделении/удалении памяти надо делать блокировку, чтобы избежать этого — дополнительные затраты времени.
> 

> Фрагментация кучи — ситуация, когда есть много свободного места, но большой блок памяти выделить не получается.
> 

```
+--+-+-+-+--+-+---+--+-+-+---+--+--+-+---+-+-+-+---+--+-+---+--+-+--+
|##| |#|#|  |#|###|  |#| |###|  |##| |###| |#| |###|##|#|   |##| |##|   (15 ячеек свободно в 9 блоках, максимум 3 ячейки подряд)
+--+-+-+-+--+-+---+--+-+-+---+--+--+-+---+-+-+-+---+--+-+---+--+-+--+
```

У 32-битной программы виртуальное адресное пространство 2 GB.
Если есть 10000 блоков памяти, равномерно разбросанных по нему, то массив больше 200 KB выделить уже нельзя.

Возможные последствия фрагментации:
1) Не получается выделить большие блоки памяти (в 64-битной программе вроде не актуально).
2) Куча медленно работает, потому что много отдельных свободных блоков.

Что делать?
1) Использование алгоритмов, которые на практике обычно дают меньшую фрагментацию.
2) Периодически выполнять дефрагментацию кучи.
Для этого нужно перемещать занятые блоки памяти, что в куче C делать никак нельзя (зато это делается в Java, C# и т.п.)

При желании систему умных ссылок и дефрагментации памяти можно реализовать в C/C++, если очень надо.
Например, такая система используется в играх Naughty Dog (говорят, на игровых консолях плохо с фрагментацией).

==================== Управление памятью ====================

Некоторые виды ошибок при работе с памятью в C:
1) null pointer deferencing: *(char*)0
Хорошо: почти наверное программа падает
2) access out of bounds: arr[-17]
Плохо: можно читать чепуху, ломать совсем другие данные, получаются редкие плохо воспроизводимые баги
Хорошо: MSVC в debug конфигурации часто выдаёт heap/stack corruption
3) uninitialized memory use: malloc + read / локальные переменные
Плохо: в релизе будут лежать какие попало данные (обычно нули)
Хорошо: MSVC в debug заполняет такие данные 0xCC — легко заметить и быстро падает
Обычно устраняется использованием calloc или использованием функций-конструкторов для структур.
4) memory leak: malloс, нет free
Плохо: память незаметно и неограниченно накапливается, никогда не освобождаясь.
На 32-битной платформе это приводит к падению с out-of-memory (OOM) ошибкой, на 64-битной лишь замедляет работу программы.
5) double free: malloc + free + free
Плохо: можно случайно освободить блок по этому адресу, выделенный кому-то другому
Хорошо: чаще всего таки падает
6) use after free: malloc + free + read/write
Плохо: можно перезаписать совсем другие данные, если этот блок переиспользован, или прочитать чушь

Далее речь пойдёт в основном о проблемах 4, 5 и 6.
Заметим, что проблема memory leak есть не только в C/C++, но и в языках высокого уровня, т.к. есть ресурсы помимо памяти.
Например, файловые дескрипторы (FILE*).

Многие ошибки возникают из-за неопределённого смысла указателя в C:
void func(…, …, int *p);
Что означает p?
Варианты:
1) опциональное входное значение типа int.
2) входной массив целых чисел int[] (возможно опциональный, возможно всегда должен быть не NULL).
3) выходное значение типа int — в него функция записывает выходные данные (может ли оно быть NULL?)
4) выходной массив целых чисел (возможно опциональный параметр, возможно нет).
5) иногда параметр является и входным, и выходным — функция обновляет данные.

Чтобы уменьшить путаницу, иногда договариваются имена параметров начинать с буквы ‘i’ (входной), ‘o’ (выходной) или ‘io’ (и входной и выходной).
Порой также добавляют букву ‘a’ (массив), либо ‘p’ (указатель).
Например:
void ComputePrefixSums(
int *iaValues, //входной массив чисел
int iSize, //длина массива
int* oaPrefixSums, //массив префиксных сумм, заполняется функцией
int *iopTotalMin //текущий минимум среди чисел (обновляется, если в заданном массиве есть число меньше)
);

Более интересный вопрос:
удаляет ли функция ComputePrefixSums указатель iaValues ?
Если посмотреть на пример посложнее (принимает массив, возвращает массив):
void doit(int *iaInput, int **opaOutput);
Возникают вопросы:
1) Удаляется ли буфер iaInput внутри функции doit?
2) Если предположить, что функция записывает в *opaOutput указатель,
должен ли вызывающий удалять этот указатель после вызова?

Эти проблемы можно решить с помощью концепции “владения”.
Единоличное владение — когда у буфера есть ровно один “хозяин”, который им распоряжается.
Он должен этот буфер или удалить, или передать владение кому-то другому.
Хозяином может быть другой объект для поля, или текущий stack frame для локальной переменной.

Пример (динамический массив):
struct Array {
int n, cap;
Item *arr; //owning
};
Структура Array описывает динамический массив, который единолично владеет своим буфером памяти arr.
Это означает, что в момент исчезновения массива нужно освободить память под arr.
Например так:
void clearArray(Array* x) { //надо сказать пользователю, что он должен вызвать clearArray
x->n = x->cap = 0; //в конце использования массива, чтобы освободить память
free(x->arr);
x->arr = 0;
}
или если массивы всегда выделяются на куче:
void freeArray(Array *x) { //надо сказать пользователю, чтобы он всегда удалял массив
free(x->arr); //через эту функцию freeArray
free(x);
}

Другой пример:
//записать массив p[0..n) в массив *a
void assign(Array* a, Item *p, int n);
Вопрос:
если вызывающий сам выделял память под p, должен ли он его удалить после вызова?
Варианты ответов:
1) Да, должен: владение буфером p не передаётся в массив при вызове assign.
Это означает, что функция assign должна скопировать все элементы p[0..n) в свой буфер.
Иначе когда вызывающий удалит p (а он может, т.к. он хозяин), массив* a окажется сломанным.
void assign(Array *a, Item* p, int n) { //copy-assign
ensureCapacity(a, n);
a->n = n;
memcpy(a->arr, p, n * sizeof(Item));
}
2) Нет, не должен: при вызове assign вызывающий передаёт владение буфером p в функцию.
Тогда массив *a становится новым хозяином буфера p, и удалять его после вызова снаружи нельзя.
В этом случае массив может “украсть” этот буфер себе, или “переместить” его (move).
Разумеется, в этом случае вызывать assign можно только если p указывает на начало буфера в динамической памяти!
void assign(Array* a, Item *p, int n) { //move-assign
free(a->arr); //здесь владение буфером a->arr заканчивается,
a->n = n; // и владение никому не передаётся — значит его необходимо удалить
a->arr = p; //массив* a принял владение буфером p
}
Конечно, даже в этом случае можно скопировать буфер, но в этом случае функция должна удалить массив *a после копирования.
При любом варианте следует написать комментарий перед функцией, чтобы вызывающий знал, как себя ведёт assign.
Вариант 1 можно считать вариантом “по умолчанию” — владение никуда не передаётся.
В варианте 2 надо написать что-то вроде //array* a receives ownership over array p (it must be allocated with malloc beforehand)

Ещё примеры:
> char *strdup(char* s);
//caller receives ownership over the returned string (and must delete it using free)

> char strchr(char s, char ch);
//no ownership passed, caller must NOT free returned pointer (it points to somewhere inside string s or is NULL)
> 

> void realloc(void buff, int size);
//caller passes ownership of buff into the function (and must not delete it)
//caller receives ownership of returned memory buffer (and must delete it)
> 

> FILE fopen(char filename, char *mode);
//caller receives ownership over the FILE
> 

> void fclose(FILE *f)
//caller passes ownership over the file f
> 

Помимо описанного выше единоличного владения, есть также вариант разделённого (shared) владения.
В этом случае у объекта может быть несколько равноправных хозяев.
Когда хозяину объект становится не нужен, и при этом он последний, кто им владеет, тогда он должен его удалить.
Этот механизм реализуется с помощью подсчёта ссылок (reference counting) — храним для объекта, сколько у него сейчас хозяев.

Смежный вопрос:
Array a;
initArray(&a);
pushArray(&a, 17);
…
Array b = a;
//???
Что можно сказать о ситуации в конце?

```
+---+     +---+
| a |     | b |
+---+     +---+
 |          |
 |          V
 |  +------------------------------------------+
 +->| 17 ... ...                               |
    +------------------------------------------+
```

Оба массива указывают на один буфер памяти — это противоречит концепции единоличного владения!
Если оставить как есть, скорее всего случится double free (буфер будет освобождаться и при удалении a, и при удалении b).
Перед этим может произойти use-after-free (если массив a будет удалён, а с массивом b будут работать).
Либо просто пользователь будет удивляться, почему при изменении a изменяется также и b.

Разрешить ситуацию можно двумя способами:
1) Занулить a после присваивания:
Array b = a;
a.ptr = 0;
a.n = b.cap = 0;
Тогда буфером снова будет владеть один b — получается передача владения без копирования
2) Запретить присваивать массивы, и завести функцию копирования содержимого:
void copyArray(Array *dst, Array* src) {
ensureCapacity(dst, src->n);
dst->n = src->n;
memcpy(dst->arr, src->arr, src->n * sizeof(Item));
}
Тогда пользователь сможет копировать весь массив (включая содержимое).
После копирования будет два массива, каждый со своим личным буфером.

Более сложная ситуация — дерево файлов и каталогов.
struct FileTree {
char *filename; //путь к файлу
FILE* fd; //открытый FILE, из которого можно читать fread-ом
FileTree *firstSon; //первый сын (если это директория)
FileTree* brother; //следующий сын (в данной директории)
FileTree *father; //директория, в которой лежит этот файл или директория
};
FileTree* root; //корневой узел
|
|
V
+—+
|tmp|<——————–
+—+

firstSon / ^ ^

/ |  father  father
/ | _____  
/ /father    
V /

+———-+ brother +—–+ brother +—-+
|readme.txt|———>|a.exe|———->|docs|
+———-+ +—–+ +—-+
|
| firstSon
V
…
Как определить, какие указатели в FileTree отражают владение, какие нет?
Например:
filename — есть владение: строки пользователя копируются strdup-ом
fd — есть владение: при удаления узла FileTree нужно закрыть этот файл
firstSon, brother — есть владение: так получается, что каждый узел владеет своими сыновьями
father — нет владения: узел не владеет своим отцом

В таком случае получается, что указатель root косвенно владеет всем деревом!
Можно написать рекурсивную процедуру удаления дерева:
void freeTree(FileTree *node) {
free(node->filename);
if (node->fd)
fclose(node->fd);
freeTree(node->firstSon);
freeTree(node->brother);
free(node);
}
При запуске для корня будет удалено всё дерево.

Можно заметить, что память в куче — не единственный ресурс, который надо освобождать.
Надо закрывать файлы, освобождать аппаратные ресурсы (например буферы видеодрайвера), убирать callback-и и пр.
Таким образом, данная проблема актуальна даже для для языков высокого уровня со сборщиком мусора.

Ещё более сложная проблема — хранение многогранника.
Он состоит из граней, рёбер и вершин:
struct Face {
…
EdgePtrArray boundary;
};
struct Edge {
…
Vertex *start,* end;
};
struct Vertex {
…
EdgePtrArray incident;
};
Легко представить тетраэдр с 4 гранями, 6 рёбрами и 4 вершинами.

Как расставить владение?
1) Указатели в Vertex.incident не проявляют владение — это просто ссылки.
2) Остальные указатели должны проявлять владение: грани владеют рёбрами на своей границе, а рёбра — своими концевыми вершинами.
Грань просто не может существовать без рёбер и вершин на своём краю!
Однако видно, что единоличное владение здесь быть никак не может: на каждую вершину указывает три рёбра, и не одно.

Ситуацию можно разрешить двумя способами:

1. Добавляем структуру многогранника, который единолично владеем всеми своими элементами:
struct Polyhedron {
FacePtrArray faces; //owning
EdgePtrArray edges; //owning
VertexPtrArray vertices; //owning
};
Все грани, рёбра и вершины нечем не владеют и ссылаются друг на друга.
Сам многогранник владеет ими всеми — они как бы “живут внутри него”.
Естественно, в этом случае в любую модифицирующую операцию надо передавать Polyhedron.
2. Используем раздельное владение (SHARED ownership).
Каждым ребром вместе владеют обе смежные грани.
Каждой вершиной вместе равносильно владеют все инцидентные её рёбра.
У каждого элемента несколько “хозяев”, и все они равноправны.

Удалять элемент нужно в тот момент, когда в него пропадёт последним хозяин.
Это обычно реализуется с помощью подсчёта ссылок (reference counting).
Будем в каждом элементе хранит счётчик ссылок — сколько у него сейчас хозяев:
struct Edge {
int refCount;
Vertex *start,* end;
};
Это число надо всегда поддерживать актуальным, а если в какой-то момент оно становится нулевым, то Edge надо удалять.
