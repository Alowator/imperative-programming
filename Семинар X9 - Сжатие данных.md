## Префиксные коды

**Вопрос**: зачем нужны коды переменной длины? (часто встречающиеся символы — короче)

**Вопрос**: в чём проблема кодов разной длины? Разобрать пример с неоднозначным декодированием:

```
A = 001, B = 11, C = 00, D = 111
→ 00111 = "AB" или "CD"?
```

**Определение**: ни один код не является префиксом другого.

**Задача**: по дереву (нарисовать на доске) выписать коды символов. Убедиться, что получилось префиксное кодирование (символы — только в листьях).

## Метод Хаффмана

**Вопрос**: как построить дерево, чтобы часто встречающиеся символы были ближе к корню?

**Алгоритм** (на доске):
1. Каждому символу — дерево из одной вершины с весом = частота
2. Пока деревьев > 1: берём два с минимальными весами, объединяем под новым корнем (вес = сумма)

**Вопрос**: какая структура данных даёт эффективный extract-min + insert? (куча)

**Задача**: на доске построить дерево Хаффмана для строки `"ABRACADABRA"`, выписать коды.

**Вопрос**: сколько будет итераций цикла для N символов? (N-1)

## Сжатие методом Хаффмана

Три шага:
1. Прочитать вход, посчитать частоты
2. Построить дерево, назначить коды
3. Второй проход — записать битовый поток

**Вопрос**: что ещё нужно сохранить в сжатом файле? (таблицу/дерево — иначе не раскодируем)

**Вопрос**: когда Хаффман сделает файл *больше* исходного? (равномерные частоты + оверхед дерева)

**Вопрос**: что будет, если применить Хаффман к уже сжатому или зашифрованному файлу? (почти ничего — у таких данных частоты байт близки к равномерным, это свойство хорошего сжатия/шифра)

**Задача (код)**: упаковка битов в байты — накапливаем в `uint8_t buf`, считаем `bit_count`, при достижении 8 пишем байт.

**Пример сжатия** `"ABRACADABRA"` (11 символов):

Частоты: `A=5, B=2, R=2, C=1, D=1`

Дерево:
```
         (11)
        /    \
       A(5)  (6)
            /   \
          R(2)  (4)
               /   \
             B(2)  (2)
                  /  \
                C(1) D(1)
```

Коды: `A=0, R=10, B=110, C=1110, D=1111`

Было: `11 × 8 = 88 бит`

Стало: `A B R A C A D A B R A` →
`0 · 110 · 10 · 0 · 1110 · 0 · 1111 · 0 · 110 · 10 · 0` = **23 бита**

**Вопрос**: а если учесть хранение таблицы кодов? (на маленьких данных оверхед съедает выигрыш; Хаффман начинает окупаться на больших текстах)

## RLE (Run-Length Encoding)

**Вопрос**: какие данные плохо сжимает Хаффман, но хорошо сжимает что-то ещё? (длинные повторы)

**Идея**: `AAAAABBBCC → 5A3B2C`

**Задача (код)**: реализовать RLE для строки — на вход строка, на выход пары (символ, количество).

**Вопрос**: что делать, если символы почти не повторяются? (RLE увеличит размер в 2 раза)

**Вопрос**: как закодировать случай «повтор длиннее 255»? (разбивать на блоки)

**Где применяется**: BMP, факсы, PCX, как этап внутри более сложных алгоритмов.

## Простые идеи в сложных форматах

**Мысль**: серьёзные форматы часто собраны из простых кирпичиков.

- **Delta encoding**: хранить разности соседних значений, а не сами значения. Хорошо для отсортированных массивов, временных рядов, звука (PCM → FLAC).
- **Varint (LEB128)**: маленькие числа в 1 байте, большие — в нескольких (старший бит = «продолжение»). Используется в Protocol Buffers, DWARF, WebAssembly.
- **Dictionary encoding**: уникальные значения выносим в словарь, вместо них храним индексы. Отлично работает на колонках с малым числом различных значений. Используется в Parquet, ORC, ClickHouse.

**Мысль**: алгоритм Хаффмана из 1952 года до сих пор работает внутри файлов, которые вы открываете каждый день — jpg, png, gzip, mp3, заголовки HTTP/2.
